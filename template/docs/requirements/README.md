# Requirements 使用说明

`docs/requirements` 保存准备实现的需求，而不是已完成架构事实。小改动也可以使用精简模板；涉及认证、分层、生成器、公共组件、配置或部署时必须写清跨项目影响。

建议文件名：`YYYYMMDD-short-name.md`。

```markdown
# 需求标题

## 背景

为什么要做，当前代码和用户问题是什么。

## 目标

- 可验证目标。

## 非目标

- 本次明确不处理的内容。

## 使用场景

- 独立运行、qiankun、模板生成后项目分别如何使用。

## 架构影响

- 所属层次和依赖方向。
- 是否修改公共 API、占位符、目录或已知偏差。
- 对新生成项目和已有项目的迁移影响。

## 配置与安全

- 环境变量、Token、权限、密钥、个人信息和日志影响。

## 生成与数据

- 是否改变 database.sql、代码生成结果、route-map 或资源 JSON。

## 验收条件

1. 可以观察和测试的结果。
2. 独立/集成模式要求。
3. 错误和回滚路径。

## 验证计划

- npm run build
- 单元/E2E/手工联调/镜像验证。

## 发布与回滚

- 分支、测试环境、镜像、资源配置和回滚方式。
```

实现完成后，稳定架构事实进入 architecture/development/operations 文档；长期设计取舍进入 `docs/decisions`。不要让 Requirements 成为唯一可找到的永久规范。
